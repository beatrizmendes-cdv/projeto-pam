GUIA DIDÁTICO DA ARQUITETURA DO FRONTEND PAM

Este guia explica a estrutura que foi proposta para acompanhar o padrão descrito pelo seu chefe. É uma organização de responsabilidades: não significa que o Next obrigue todos os projetos a usar esses nomes.

1. PRIMEIRO: O QUE SIGNIFICA ARQUITETURA?

Arquitetura, aqui, significa decidir onde cada responsabilidade fica.

Uma tela pode precisar:
- Buscar registros.
- Mostrar uma tabela ou cartões.
- Filtrar os resultados.
- Abrir um formulário.
- Validar o que foi digitado.
- Transformar os dados para a API.
- Salvar e atualizar a listagem.

Tudo isso poderia caber em um único arquivo. O problema é que fica difícil encontrar a parte que você precisa mudar e entender por que uma alteração afetou outra coisa.

A estrutura proposta separa essas tarefas em arquivos pequenos com objetivos claros. Não é necessário adicionar novas camadas além delas para começar.

3. PAGE.TSX: A ENTRADA DA ROTA

No App Router, app/simulations/page.tsx representa a página /simulations.

Exemplo:

import SimulationsClient from './client-simulations';

export default function SimulationsPage() {
  return <SimulationsClient />;
}

O Next encontra page.tsx pela convenção de arquivos. Quando você acessa a rota, esse componente participa da montagem da página.

Por que deixar pequeno?
Porque a entrada da rota fica fácil de reconhecer e, no futuro, pode receber responsabilidades do servidor, como carregar informações iniciais, sem misturar tudo com campos e cliques.

Não é obrigatório que todo page.tsx seja pequeno. É o padrão de organização que você decidiu seguir. Por enquanto, uma função que renderiza o client é suficiente.

4. CLIENT-SIMULATIONS.TSX: A TELA INTERATIVA

O arquivo começa com:

"use client";

Aqui ficam os hooks, eventos e estado da tela: consultar simulações, observar a busca, mostrar cartões, controlar o registro selecionado e abrir/fechar um modal quando essa funcionalidade for implementada.

O nome client-simulations.tsx não tem poder especial. O que define a fronteira cliente é a diretiva use client. O arquivo pode ser chamado de outra forma conforme a convenção da equipe.

Client Component também pode participar da renderização inicial no servidor. Não significa que todo código seja executado exclusivamente no navegador, nem que seja seguro acessar window diretamente durante qualquer renderização.

Para mover sua tela:
1. Copie o conteúdo atual de page.tsx para client-simulations.tsx.
2. Mantenha use client no novo arquivo.
3. Renomeie a função para SimulationsClient.
4. Substitua page.tsx pelo pequeno exemplo anterior.
5. Confira imports e a página.

Não mova apenas metade do JSX e deixe os hooks desconectados. A primeira separação pode levar a tela interativa inteira de uma vez.

5. LAYOUT.TSX: A ESTRUTURA COMPARTILHADA

O layout envolve as páginas. No seu projeto ele organiza Header, sidebar e main.

children representa a página correspondente à URL atual:

Layout
  Header
  Sidebar
  main
    children -> page.tsx -> componente cliente

Não repita Header e sidebar em cada formulário ou tela.

O ReactQueryProvider precisa envolver os componentes que usam TanStack Query. Se ele envolve children, as páginas podem consultar os dados. A mudança de page para client não exige criar outro provider por tela.

6. COMPONENTS: PEÇAS VISUAIS REUTILIZÁVEIS

Card recebe label, value e unit. Ele mostra o que recebe. Não precisa saber de Swagger, banco ou URL.

SimulationBox recebe o nome e os demais dados disponíveis. A página busca a lista e renderiza uma caixa por registro:

simulations.map((item) => (
  <SimulationBox key={item.id} name={item.name} />
))

Separar apresentação e consulta facilita usar o componente em mais lugares.

Os dados precisam existir de verdade. Se a API retorna somente id e name, não apresente total=15 ou uma data fixa como se viessem do banco. Exiba um placeholder ou deixe o campo fora até implementar a informação.

7. HOOKS: CONSULTA E ESTADO DOS DADOS DO SERVIDOR

Um hook personalizado reúne lógica React reutilizável. useSimulation envolve useQuery:

"use client";

import type { ResponseSimulationDto } from '@/clients/projeto-pam';
import { simulationApi } from '@/lib/api';
import { useQuery } from '@tanstack/react-query';

export function useSimulation() {
  return useQuery<ResponseSimulationDto[]>({
    queryKey: ['simulation'],
    queryFn: async () => {
      const response = await simulationApi.simulationControllerFindAll();
      return response.data;
    },
  });
}

queryKey: identifica os dados no cache. Não é a URL.
queryFn: função que executa a busca quando o TanStack precisa.
await: espera o resultado assíncrono sem travar toda a interface.
response.data: conteúdo da resposta Axios.
ResponseSimulationDto[]: tipo esperado da lista, não uma conversão ou validação dos dados.

A página recebe data, isPending, isError e refetch, entre outras propriedades. Não precisa copiar a mesma lista para um useState só para exibi-la.

Use hooks no topo de componentes ou outros hooks, nunca dentro de if, loops ou onClick.

8. SCHEMA.TS: AS REGRAS DO FORMULÁRIO

Exemplo de simulações:

import { z } from 'zod';

export const simulationSchema = z.object({
  name: z.string().trim().min(1, 'Informe o nome da simulação'),
});

export type SimulationFormValues = z.infer<typeof simulationSchema>;

z.object descreve um objeto. name é uma propriedade desse objeto. z.string exige texto. trim remove espaços nas extremidades. min(1) exige pelo menos um caractere após essa remoção.

z.infer cria o tipo TypeScript correspondente ao schema. Assim você não precisa escrever o mesmo formato manualmente em dois lugares.

TypeScript e Zod são diferentes:
- TypeScript verifica seu código durante o desenvolvimento.
- Zod verifica os valores enquanto o programa roda.

O tipo gerado pelo OpenAPI descreve o contrato da API. O schema do formulário descreve regras da experiência de preenchimento. Eles podem ter campos iguais, mas não precisam ser idênticos.

Não é necessário criar validações complexas para um campo simples. Comece pelas regras reais do formulário e mantenha a validação do backend também.

9. CREATE-EDIT-SIMULATION-FORM.TSX: OS CAMPOS E O ENVIO

Esse componente usa React Hook Form para acompanhar valores, erros e submissão. Zod entra por meio do zodResolver. MUI fornece os campos e botões.

Responsabilidades:
- Criar useForm com defaultValues.
- Conectar o schema ao resolver.
- Renderizar os inputs.
- Exibir mensagens de erro.
- Chamar handleSubmit.
- Entregar valores válidos para a função onSubmit recebida.
- Impedir envio duplicado enquanto a operação estiver em andamento, conforme a integração escolhida.

Diferença importante:
defaultValues (plural) pertence à configuração do useForm.
defaultValue (singular) é usado por outras APIs, como useWatch para um campo.

Um mesmo formulário serve para criar e editar:
- Criação: valores iniciais vazios.
- Edição: valores iniciais do registro selecionado.

defaultValues não acompanha automaticamente toda mudança de registro. Quando implementar troca entre registros mantendo o mesmo formulário montado, use reset com os novos valores ou uma estratégia de remontagem por chave. Não implemente isso antes de precisar, mas saiba por que os campos podem manter valores antigos.

Formulário não é sinônimo de modal. O formulário pode ser exibido em um Dialog, página ou painel. A tela cliente decide onde ele aparece.

10. FORMAT-PAYLOAD.TS: TRANSFORMAR PARA O CONTRATO DA API

Payload é o objeto enviado como corpo da requisição.

Exemplo:

import type { CreateSimulationDto } from '@/clients/projeto-pam';
import type { SimulationFormValues } from './schema';

export function formatSimulationPayload(
  values: SimulationFormValues,
): CreateSimulationDto {
  return { name: values.name.trim() };
}

Em simulações, essa transformação é pequena. O arquivo existe por consistência com o padrão da equipe.

Em turbinas, ele é mais útil: o formulário pode ter latitude e longitude separadas, mas a API recebe coordinates: { type: 'Point', coordinates: [longitude, latitude] }.

Essa função deve receber valores, retornar um objeto e não fazer requisições. Use .ts porque não há JSX.

Campos numéricos precisam ser tratados com cuidado: inputs podem entregar strings. Escolha uma estratégia explícita de conversão/validação no formulário/schema antes de enviar. Campo vazio não deve virar zero sem uma decisão intencional.

11. MUTATIONS: SALVAR ALTERAÇÕES

useQuery cuida de leitura. useMutation é apropriado para criar, editar e excluir.

Fluxo simples sugerido:
1. Usuária clica em salvar.
2. handleSubmit executa a validação do formulário.
3. Se houver erro, o formulário mostra a mensagem.
4. Se estiver válido, onSubmit recebe os valores.
5. A tela usa formatSimulationPayload.
6. Uma mutation chama o método de criação ou atualização do cliente.
7. Após sucesso, invalida a query ['simulation'] para atualizar a lista ativa.
8. A tela fecha o modal quando essa funcionalidade existir.

Uma chamada assíncrona deve ser aguardada se o formulário precisa acompanhar a conclusão. Não trate um erro de rede como cadastro bem-sucedido e não feche o formulário antes de saber o resultado.

Para editar, você precisa do ID do registro selecionado. Esse ID pode ser passado separadamente ao método de atualização, conforme a assinatura gerada. Não presuma que o ID pertence ao corpo da requisição.

12. LIB/API.TS E CLIENTS/PROJETO-PAM

lib/api.ts configura o endereço do backend e cria objetos prontos para uso:

simulationApi
turbinesApi
turbineCatalogApi

clients/projeto-pam contém o código produzido pelo OpenAPI Generator. É a ponte HTTP entre frontend e backend. A biblioteca não contém o banco e não copia o backend para o navegador.

Não confunda:
- client-simulations.tsx: componente da interface.
- clients/projeto-pam: biblioteca de comunicação HTTP.

Não edite os arquivos gerados para corrigir regras de negócio. Corrija a origem e gere novamente. O ajuste de compatibilidade do Axios já foi colocado no script de geração para não depender de edição manual a cada execução.

13. FLUXO COMPLETO DE LEITURA

Usuária abre /simulations
  -> Next encontra page.tsx
  -> page renderiza SimulationsClient
  -> SimulationsClient chama useSimulation
  -> TanStack executa queryFn quando necessário
  -> simulationApi faz GET /simulation
  -> Controller do Nest recebe
  -> Service consulta o PostgreSQL pelo TypeORM
  -> Backend devolve JSON
  -> Axios entrega response.data
  -> TanStack atualiza o estado da consulta
  -> React renderiza SimulationBox para cada registro

Com cache existente, a tela pode receber dados já armazenados. O comportamento de nova busca depende da configuração do TanStack. Não é necessariamente uma nova requisição em toda renderização.

14. FLUXO COMPLETO DE ESCRITA

Usuária preenche formulário
  -> React Hook Form acompanha valores
  -> Zod valida no envio
  -> onSubmit recebe valores válidos
  -> format-payload monta o DTO
  -> mutation chama cliente HTTP
  -> backend valida novamente
  -> service salva no banco
  -> resposta confirma sucesso
  -> cache/listagem é atualizado

A validação frontend melhora a experiência. A validação backend continua necessária, porque uma API pode receber chamadas de outros programas.

15. MUI, TAILWIND E SEUS COMPONENTES PODEM CONVIVER

Mantenha h1, p e div com Tailwind. Reutilize Card e SimulationBox. Use MUI para TextField, Table, Button, Alert e outros componentes que realmente ajudam.

Você não precisa trocar todo texto por Typography. Para ajustar um Button do MUI, sx pode definir cor, fonte, borderRadius e hover. disableElevation remove a sombra e textTransform: 'none' mantém a capitalização digitada.

Ao combinar estilos, evite declarar a mesma propriedade de várias formas sem entender a prioridade. Um caminho simples é Tailwind nos seus contêineres/HTML e sx nos ajustes internos do componente MUI.

16. O QUE NÃO PRECISA MUDAR PARA ESSA REORGANIZAÇÃO

- Não precisa mudar rotas do backend.
- Não precisa regenerar cliente só por mover JSX para client-*.tsx.
- Não precisa mudar o banco.
- Não precisa transformar todos os componentes em MUI.
- Não precisa criar outra biblioteca de estado.
- Não precisa implementar o modal antes de terminar a separação da tela.

17. QUANDO REGENERAR O CLIENTE

Quando o contrato da API mudar: novos campos, entrada, saída ou endpoints.

Dentro de backend, executar pessoalmente:

npm run swagger:gen
bash api/scripts/generate.sh

Primeiro gera openapi.json; depois gera a biblioteca. O Swagger precisa descrever entrada e saída. O gerador não descobre o contrato lendo o service ou consultando o banco.

Não edite openapi.json à mão como solução permanente. Corrija decorators/DTOs no backend e gere o documento.

18. SEQUÊNCIA DE APRENDIZADO PARA CONTINUAR

Passo 1: separar uma tela em page e client, mantendo comportamento.
Passo 2: repetir a organização nos outros domínios.
Passo 3: definir schema do formulário de simulação, começando pelo nome.
Passo 4: escrever o formulário com valores iniciais e mensagens.
Passo 5: escrever o formatter para CreateSimulationDto.
Passo 6: conectar uma mutation ao método real gerado.
Passo 7: atualizar a listagem após salvar.
Passo 8: implementar edição e depois o modal conforme o escopo desejado.
Passo 9: aplicar os conceitos ao catálogo e às turbinas.

Faça uma etapa por vez e observe o resultado. Se houver erro, identifique em qual fronteira ele aconteceu: formulário, formatter, cliente, rede ou backend. Isso evita alterar várias partes sem necessidade.

19. PERGUNTAS PARA VOCÊ SABER SE ENTENDEU

- Qual arquivo define a rota? page.tsx.
- Onde fica a tabela e o estado do modal? No componente cliente da tela.
- Onde ficam os campos de cadastro/edição? No create-edit-form.
- Quem valida os valores do formulário? Zod integrado ao React Hook Form.
- Quem converte latitude/longitude para o objeto esperado pela API? format-payload.
- Quem faz HTTP? O cliente gerado, configurado em lib/api.ts.
- Quem gerencia cache e estados da consulta? TanStack Query.
- Quem acessa o banco? O backend, por meio do service/repositório.
- Mover a page para client exige gerar a library? Não.
- Adicionar um campo de resposta no backend exige atualizar o contrato e o cliente? Sim, para que o frontend receba a tipagem atualizada.

Este guia descreve a proposta discutida. Verifique os arquivos atuais antes de aplicar exemplos: o projeto está evoluindo e a estrutura do sistema oficial pode detalhar convenções adicionais.
